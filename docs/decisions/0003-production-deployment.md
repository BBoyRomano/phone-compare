# 0003: Continuous production deployment

## Status

Superseded by [0006: Multi-app monorepo and isolated delivery](0006-multi-app-monorepo.md) — 2026-08-11

## Decision

Run the public application on the existing Cloudflare Worker named `phone-compare`. Use GitHub Actions as the production deployment orchestrator and Wrangler as the deployment primitive. The deployment consumes the Cloudflare configuration generated by the Vinext/Vite production build rather than maintaining a second Worker configuration.

`main` is the single production branch and is always intended to be deployable. Normal changes reach it through the protected pull-request process. Every push or merge to `main` that can affect production automatically verifies, builds, and deploys that exact commit; no separate discretionary deployment decision is required. Commits limited entirely to the explicitly reviewed non-production paths in the workflow may skip Worker verification, build, and deployment because those files cannot change the production artifact. Ordinary CI still verifies those commits, and any path not explicitly ignored triggers production deployment by default. A manual dispatch from `main` is only an operational fallback. The GitHub `production` environment supplies the existing Cloudflare credentials to the deployment step and identifies `https://phone-compare.bboyromano.workers.dev` as the production URL.

Serialize production workflow runs in one production-specific concurrency group without cancelling an in-progress run. GitHub Actions retains one pending run and replaces that pending run when a newer eligible `main` commit arrives. Intermediate commits can therefore be superseded before deployment, while the running deployment finishes and the pipeline converges on the newest pending `main` state. This also prevents an older concurrent deployment from completing after a newer one.

Treat protected `main` as the production source of truth. GitHub production Deployments and Cloudflare Worker versions and deployments provide the operational deployment history. GitHub Releases, release tags, and semantic application versioning are not part of routine delivery. Agents must not create or maintain Releases, release tags, or version bumps unless a future explicit owner-controlled governance decision introduces that requirement. Do not introduce a release branch, staging branch, second long-lived integration branch, or canary/progressive rollout until evidence justifies a separate decision.

Selecting or configuring a custom domain remains an owner-controlled later decision. Unattended application agents receive no independent decision or credential path for direct production deployment: production changes flow through the protected `main` branch and this pipeline.

## Why

- A successful protected merge already represents the production decision, so an additional discretionary approval after merge would add delay without adding a distinct control.
- Repository-native verification and deployment make the deployed commit, logs, and outcome auditable in one place.
- Wrangler deploys the framework-generated Worker artifact directly and preserves the configuration that was already live-validated.
- Native path filtering avoids rebuilding and redeploying the same Worker artifact for changes proven to be production-inert.
- Serialized, non-cancelling runs avoid interrupting an active production change while collapsing obsolete queued work.
- Cloudflare's version history provides a simpler initial rollback mechanism than automated rollback logic in the workflow.

## Alternatives considered

- **Cloudflare Workers Builds/Git integration:** rejected because running a second deployment orchestrator would create duplicate or racing production paths.
- **A separate release, staging, or production branch:** rejected because protected `main` is the deployable integration point and a second long-lived branch would add drift and promotion work.
- **A second approval after merge:** rejected because the reviewed merge to protected `main` is the owner-controlled production decision.
- **Canary or progressive deployment:** deferred until traffic, risk, or operational evidence justifies the added complexity.
- **Automatic rollback after smoke-test failure:** deferred because Cloudflare already retains deployable versions and a safe automatic rollback policy needs more incident evidence.

## Tradeoffs and revisit conditions

A deployment can succeed before its live smoke check fails. That failure remains visible in GitHub Actions and operators can select a previous Cloudflare Worker version; this initial pipeline does not guess whether rollback is safer than investigation. Because only the newest pending run is retained, an intermediate `main` commit may never deploy when commits arrive quickly, but the system still converges on the newest protected state.

Revisit this decision if production risk requires staged traffic, rollback can be made deterministic from operational evidence, a custom domain is owner-approved, or the current runtime or orchestrator no longer meets reliability, security, or operating-cost needs.
